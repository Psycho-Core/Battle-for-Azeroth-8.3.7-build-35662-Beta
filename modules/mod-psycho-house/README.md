# mod-psycho-house - build plan and full reference

This is my working set for turning the housing prototype into **mod-psycho-house**, a
self-contained player-housing system for BfA 8.3.7 build 35662 running on the
BfaCore Reforged tree. Client is unlocked, so client-side assets are on the table; the
client is still 8.3.7, so everything I build has to be expressed in systems 8.3.7
actually ships.

Everything for housing lives in this one folder. Two draft modules are inside it, one
ported from Midnight and one built only from 8.3.7 ids:

```
modules/mod-psycho-house/
  README.md              this file
  01-...09-....md        the reference set
  10-draft-modules.md    the two drafts, side by side
  11-verification-ledger.md  where every number comes from, and what is unchecked
  12-midnight-item-port.md   item by item: extract, convert, write the DB2 rows, package,
                         verify - plus how the housing menus are rebuilt client side
  13-mod-psychohouse-design.md  the third draft: one island house per character, why
                         every decision in it is the 8.3.7-compatible one, and what the
                         build does and does not provide
  14-settings-and-commands.md  all 29 server settings, all 44 commands, the six client
                         settings, and the three-way check that keeps them in step
  data/                  CSV snapshots: 1 056 stock lines, 739 item ids, 618
                         decor-to-gameobject mappings, 39 of 39 npc ids, and the raw
                         per-vendor captures
  generated/             source asset index (28 314 constants, 988 decor-shaped) and the
                         full town centre stock register (39 vendors, 1 056 lines)
  08-...appendix         every decor-shaped constant, regenerated by tools/housing/build_appendix.py
  vendor-slugs.txt       the 39 vendor slugs every scraper consumes
  drafts/
    midnight-port/       draft A - retail content, retail numbers
    bfa-native/          draft B - 8.3.7 ids only, gold only
  src/game/Housing/      the C++ core the drafts copy: 21 files, the manager, the
                         neighbourhoods, the houses, the Endeavor engine, the four NPC

  src/scripts/Housing/   commands (46 of them), player/world/guild hooks, loader
  sql/world/             the schema update
  sql/characters/        the character-side update
  sql/generated/         output of the world-DB harvest (empty until run)
  addon/HousingUI/       the client addon: Core.lua (transport, grid snapping) and
                         Menu.lua (the nine-tab housing window)
  legacy-prototype/      the original prototype notes and patches, kept verbatim as

  tools/housing/         scrapers, indexers, the draft builder, the installer,
                         the CMake patch and the audit
```

I read nine sources for this (listed in doc 01 sec.11) and I have been careful to keep
three kinds of statement apart:

- **Retail fact** - published by Blizzard or a guide, with a number attached. Quoted.
- **BfA capability** - something 8.3.7 genuinely supports. Verified against the tree.
- **My decision** - design calls, budgets, prices, scoring. Mine, not Blizzard's.

If a document says "unknown", it means I could not verify it and I am not going to
invent it. There are a lot of unknowns in retail's quest table because Blizzard does not
publish entry ids for the interior quests.

## Executive summary

Retail housing is five systems wearing one hat: **ownership** (plots, warband, moving),
**building** (rooms, exteriors, budgets, house levels), **decor** (collection, placement,
dye, pet beds), **community** (neighborhoods, permissions, Endeavors), and **sharing**
(blueprints). 8.3.7 gives me usable raw material for four of the five almost intact, and
one place where I have to substitute hard: **the client has no housing UI and no
modular room geometry**, so rooms become "shells" and the UI becomes an addon.

What 8.3.7 already has that does the heavy lifting:

- **Phases** (`PhaseShift`, 16-bit ids) - the entire neighborhood/plot isolation model.
  Plot phases are `10000 + slot * 64 + plot` in 8.3.7's uint16 space, so 255
  neighbourhoods fit before the interior range begins.
- **Instanced and non-instanced maps** - one map per neighborhood, one interior map.
- **Game objects** - every furniture piece, tree, brazier, wall, tent and cart already in
  the game is a GO template I can spawn, scale and rotate.
- **Battle pets** - pet beds are just creature spawns in a plot phase.
- **Scenarios + worldstates** - Endeavor progress and the intro questline.
- **Currencies + vendors + gossip** - the entire econ and shop layer.
- **The garrison tables and `GarrisonPlot` scaffolding** - proof this core can already do
  "player owns a plot on a private map", which is 80% of the hard part.

What it does not have, and what that costs me: no housing DB2, no room system, no dye, no
blueprint exchange, no Housing Dashboard. Those are additions, and docs 05 and 06 are
about paying for them in that order.

**The build order I am committing to** (detail in doc 05):

```
P0  ownership + travel + persistence            (prototype already does this)
P1  decor catalogue from my own GO templates    (harvest tool + vendor economy)
P2  house levels, budgets, rooms as shells      (retail-accurate numbers, apply via contractor)
P3  Endeavors as monthly BfA-content events     (worldstates + Phase 3.5 of my module)
P4  dyes (Alchemy/Inscription) + pet beds       (custom items + GO reshade)
P5  blueprints as import/export codes           (addon message + compressed blob)
P6  art pass: custom WMO/ADT housing zone       (client patch, replaces the anchor map)
```

Estimated 14-18 weeks of evenings for P0-P5 against a codebase that already compiles and
runs; P6 is art-bound, not code-bound.

## Audit pass, twenty-third revision

The twenty-second pass fixed the settings layer. This one went back to the retail reference and
asked, row by row, whether the thing doc 01 describes is the thing the code does. Two systems
were half-built and one was described as finished while doing half of what its own row claimed.

| # | Finding | Fix |
| --- | --- | --- |
| 128 | Advanced mode is "free placement, free rotation on three axes, scaling". The code carried yaw and scale, so a painting could not hang tilted and a banner could not lie flat. Doc 02's row said "rotate" and was read as done | `pitch` and `roll` end to end: two new columns, two placement fields, a quaternion built from all three angles, a clamp at +-90 degrees, optional trailing fields on `C:PLACE` and `C:MOVE` (an addon that does not send them is unchanged), tilt boxes and a step button in the Placed tab, and `.housing tilt` for changing the tilt alone |
| 129 | Blueprint codes were version 1 with no room for tilt, and the decoder's bounds check counted the three coordinates but then read nine bytes - a truncated code read past the end of its own buffer | Version 2 adds one packed tilt byte per piece (two nibbles, 12 degrees apart over +-90); version 1 codes still decode with the tilt at zero. | 130 | Doc 06 sec.4 promised the retail pet bed - assignment, Stationary or Roaming, caps of 100 indoors and 25 outdoors - and the code spawned a fixed creature per decor row. ## Audit pass, twenty-second revision

The twenty-first pass asked whether a feature had been written. This one asked the question
the user actually asked: is the *package* complete - every system, every feature, every
setting. Settings turned out to be the weakest layer, because a setting has three places to
live (the conf file, the code that reads it, the document that explains it) and nothing was
comparing them.

| # | Finding | Fix |
| --- | --- | --- |
| 122 | Fourteen of the 29 settings were documented nowhere but the conf file's own comments, and there was no single place listing what the realm can change | Doc 14: every setting with its default, its clamp and whether a reload picks it up; every command with its arguments and permission |
| 123 | Nothing could tell a setting that was being applied from one that was being ignored. `LoadConfig` read 29 keys and forgot every value the moment it had copied it into a field | `LoadConfig` records each key with the value it kept after clamping, `GetConfigSnapshot` returns that record, and `.housing config [filter]` prints it.
